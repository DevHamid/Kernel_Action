# Android kernel build via GitHub Actions (DevHamid)

## Architecture: two repos, cloud-only build
- **Source kernel**: `DevHamid/LKGeek_sdm660`, branch `devhamid-remastered`. Local clone: `/srv/ssd/ksrc/lkdev-devhamid-remastered`. Defconfig: `arch/arm64/configs/vendor/wayne-oss-perf_defconfig`.
- **Workflow repo**: `DevHamid/Kernel_Action`, branch `Kernel_Action`, local clone `/srv/ssd/kaction`. Its `.github/workflows/build-kernel.yml` clones the source at `KERNEL_SOURCE_BRANCH` (default `devhamid-remastered`).
- Pushing to the **source** repo does NOT build. The build auto-triggers only on a push to the **Kernel_Action** branch. To rebuild after a source change, make a trivial bump (append a `# rev <sha>` comment) to `kaction/config.env`, commit, push Kernel_Action.
- Artifacts (boot.img, AnyKernel3, resolved-config) are on the run page; direct `api.github.com/.../artifacts` download returns 401 without auth — give the user the run URL instead. For a truly no-auth raw download, have the workflow force-push the built files to a branch on success (orphan `kbuilds`; force-push replaces history each build): `git push -f https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${GITHUB_REPOSITORY}.git kbuilds`, then fetch at `https://github.com/<owner>/<repo>/raw/kbuilds/boot.img`.
- Credentials live in `gh`, not the shell: the CLI is installed at `/opt/data/.local/bin/gh` (not on PATH) and is authenticated as DevHamid with `repo`+`workflow` scopes — so run logs ARE readable first-class. `gh api repos/<owner>/<repo>/actions/jobs/<job_id>/logs --allow-escape-sequences` returns the full log (the `--allow-escape-sequences` flag matters — without it the ANSI escapes block/garble the read). Grep the stripped log for the real compiler error (e.g. `error:[`) rather than reading it whole. Plain unauthenticated `curl` still 403s on `/actions/runs/<id>/logs` and 401s on `/artifacts/<id>/zip`, and `$GITHUB_STEP_SUMMARY` renders only to signed-in viewers. Only where `gh` is unavailable/unauthenticated, fall back to publishing the log from the workflow: add `permissions: contents: write` at workflow top level and a `if: failure()` step that commits `build.log` + `out/.config` to a `build-logs` branch (`git push https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${GITHUB_REPOSITORY}.git build-logs`), then `git clone -b build-logs --depth 1 https://github.com/<owner>/<repo>.git`. Also `tee build.log` with `set -o pipefail` in the compile step, or the log stays empty when make fails.
- To verify a finished run WITHOUT any API/gh auth (no token on the box), poll the publish branch over the SSH deploy key instead of the API — `scripts/watch_kbuilds.sh` does this loop (baseline SHA in, new commit + file listing out; the branch only advances on a successful build, so a change means a bootable artifact exists): `git ls-remote --heads origin` first to confirm the branch exists and its head SHA; then `GIT_SSH_COMMAND="ssh -i ~/.ssh/id_ed25519_github_ka -o IdentitiesOnly=yes" git fetch origin kbuilds` — the commit lands on `FETCH_HEAD` (or `refs/heads/kbuilds` if you fetch with `origin kbuilds:kbuilds`). A fresh commit timestamp (`git log -1 --format='%ci' FETCH_HEAD`) confirms the build finished; `git ls-tree -r --name-only FETCH_HEAD` lists shipped artifacts without downloading them (`Image.gz-dtb`, `boot.img`, `config.txt` on `kbuilds`). Then read the committed artifact directly to verify the shipped config: `git show FETCH_HEAD:config.txt | grep CONFIG_<SYMBOL>` (also `boot.img`, `Image.gz-dtb`). Do the same with `build-logs` to read a failure log. Direct no-auth download of a shipped file: `https://raw.githubusercontent.com/DevHamid/Kernel_Action/raw/kbuilds/boot.img` (returns 200 when the branch exists; works for `boot.img`, `Image.gz-dtb`, `config.txt`).
- Poll runs with `curl -4` and `python3 -c` on `['status']`/`['conclusion']`; a single-run endpoint is reliable while the run-list endpoint intermittently resets. GitHub API JSON may contain control characters — parse with `json.loads(..., strict=False)` (strict mode raises JSONDecodeError).
- The GitHub API core rate limit (60/hr) hits 0 quickly under polling; `curl -4 https://api.github.com/rate_limit` shows `remaining 0`. Don't wait — poll the web UI signed-out instead: `curl -4 -s https://github.com/<owner>/<repo>/actions | grep -oE '#<run>:|In progress|completed successfully|failed'`. Return to the API once `remaining` is positive.
- Never build locally. The local tree is only for editing + pushing; the user insists on cloud builds and on working inside `/srv/ssd` only.

## CI builds the remote branch — verify what the runner actually cloned
- Before diagnosing "your change broke the build" from local symptoms, prove what the runner compiled. The workflow clones the source at `KERNEL_SOURCE_BRANCH` from `config.env`; a symbol or line present in the local tree can be absent on the branch CI builds, so a local reproduce can fail where CI is green (and the reverse). Diff them first: `git fetch origin <branch> && git log --oneline HEAD..origin/<branch>` and `git diff HEAD origin/<branch> -- <path>`.
- Prove a green run with artifact bytes, not the green check: download the run's artifact zip with the authenticated gh token (`gh api repos/<owner>/<repo>/actions/artifacts/<id>/zip > img.zip`, or `curl -sL -H "Authorization: token $TOK"`), then assert `len(data)`, gzip magic `1f8b`, and the sha256 of `Image.gz-dtb`. A real `Image.gz-dtb` in the artifact set proves the kernel compiled and linked; the badge alone does not.
- Grep the job log for interactive-kconfig stalls to prove a prompt-free run: `grep -c 'Error in reading\|Bitmask of available' <job-log>` must be 0.
- Fetch the full run log as a zip (`/actions/runs/<id>/logs`) and extract the per-job `.txt` with python `zipfile`; the `/actions/jobs/<job_id>/logs` endpoint can return an empty body. Grep the extracted job log for the make invocations actually executed (`grep -nE 'make -j|olddefconfig|defconfig'`) to confirm which build steps ran, instead of assuming the workflow you pushed is the one that ran.
- Label any claim about what a build did — or will do — as unverified until the run returns; state predictions as hypotheses. A confidently stated wrong prediction sends the diagnosis the wrong way and costs the user trust: run the check, then correct the record if the output contradicts you. When predicting a branch will hit a known failure mode, name the exact precondition you verified (e.g. "this branch's defconfig leaves the value empty") rather than a proxy like "the symbol exists" — a prediction stated as "the symbol is present so it will prompt" has been falsified by a branch that carries the symbol, sets a value, and built green.

## Local kconfig-stage reproduction without a host toolchain
- To test whether a defconfig symbol triggers an interactive kconfig prompt on this 4.19 tree without bison/flex/clang, copy the prebuilt `scripts/kconfig/zconf.tab.c` and `zconf.lex.c` from `/srv/ssd/kernel-work/scripts/kconfig/` into `<O=dir>/scripts/kconfig/`, then run `make -j$(nproc --all) CC=gcc O=<dir> ARCH=arm64 CLANG_TRIPLE=aarch64-linux-gnu- LD=ld.lld <defconfig> < /dev/null`.
- This reproduces the config stage only. A local full compile is never a valid substitute for CI evidence — scope any local result to the stage it actually exercised before citing it for or against a build.

## Per-build variable isolation: one defconfig var per build (B5/B6/B7)

- To isolate a bootloop root cause, run builds that differ by exactly ONE defconfig variable. The workflow exposes three workflow_dispatch inputs (CONFIG_KSU_SUSFS_SUS_MOUNT, CONFIG_KSU, CONFIG_KSU_SUSFS); an Inject step appends each chosen value as a `=n`/`=y` line to `arch/${ARCH}/configs/${KERNEL_CONFIG}` at build time.
- Do not edit config.env between builds for a variable the workflow input already covers — the input overrides it at inject time. A push to Kernel_Action triggers the build; the head SHA identifies which config ran.
- The workflow's Inject step only writes a symbol when the env var is exactly `n` (echoes `CONFIG_...=n` into the defconfig). A `y` or unset value in config.env is a NO-OP — the defconfig's own default stands unchanged. If you need to force a symbol ON via this step, you cannot; edit the defconfig file directly. A `y` in config.env therefore does not guarantee the symbol is enabled — read the resolved `config.txt` on `kbuilds` to see what actually compiled.
- Verify the resolved config in the committed `config.txt` on `kbuilds`, not the defconfig source — the defconfig file itself may not reflect the injected values.
- B5: CONFIG_KSU_SUSFS_SUS_MOUNT=n, CONFIG_KSU=y, CONFIG_KSU_SUSFS=y — suspects the SUS mount hook.
- B6: CONFIG_KSU=n, CONFIG_KSU_SUSFS=n — KSU + SusFS fully out.
- B7: vanilla baseline, zero custom patches — tests whether the upstream `devhamid-remastered` merge itself is broken.
- Decision rule: B7 boots → upstream fine, problem is patches/config → fixable. B7 loops → upstream merge broken → rebase from clean CIP/upstream, salvage your per-commit fixes onto the clean base.

## Boot-image forensics

- Component-level inspection of a boot image (header, kernel slice, ramdisk, appended DTB) and comparison across two images without unpack tools: `references/boot-image-forensics.md`. Use it to isolate bootloop cause between control images before trusting any custom build.
- Two images with IDENTICAL kernels can still boot differently — the ramdisk is then the whole difference, and a Magisk-injected ramdisk is the usual cause (it shadows pstore, see the pstore section). Prove component equality field by field before theorising: kernel slice sha1, appended DTB bytes, then the ramdisk cpio entry list. A ramdisk diff must be reported as an entry-level table (`name | mode | size | data-sha1 | SAME/DIFF/ONLY-S/ONLY-D`), not a single size delta — the sizes alone cannot tell a Magisk injection from a genuine ramdisk edit.
- The header `id` field is NOT always sha1. Two packer families are in play on this tree: sha1 over (kernel || kernel_size || ramdisk || ramdisk_size || second || second_size || header-with-id-zeroed), stored as 20 bytes then zero-padded to 32; and **sha256 over the bare `kernel || ramdisk` byte concatenation** (no sizes, no header), stored as a full 32 bytes. Identify which by trying both and comparing to the stored field before you rewrite an image — a rebuilt image with the wrong id formula is the exact class of bug you are trying to fix. Recipe: `references/boot-image-forensics.md`.

## Publish branch taxonomy: kbuilds / test-images / build-logs

- `kbuilds`: latest SUCCESSFUL build. Contains exactly `Image.gz-dtb`, `boot.img`, `config.txt`. The branch only advances on success — a new commit means a bootable artifact exists. Download the fresh `boot.img` from here once the target build completes.
- `test-images`: older experimental set (B1–B4 boot.img variants, ak3 zip). Do NOT flash these images on a current build — they are stale.
- `build-logs`: failure logs (`build.log` + `out/.config`) committed by the workflow on failure. Read via `git show FETCH_HEAD:build.log`.
- Do not mix artifacts across branches — provenance is per-branch. A `config.txt` from one build does not authoritatively describe a `boot.img` from another.

## Pushing to both repos (two deploy keys)
- Two separate SSH deploy keys exist: `id_ed25519_github` (LKGeek_sdm660) and `id_ed25519_github_ka` (Kernel_Action). GitHub accepts only the key registered for the repo in play; a single host block with both IdentityFiles is unreliable.
- For the kernel repo, plain `git push origin devhamid-remastered` works (default `github.com` config maps to `ssh.github.com:443`).
- For Kernel_Action use the working override:
  ```
  git remote set-url origin "ssh://git@ssh.github.com:443/DevHamid/Kernel_Action.git"
  GIT_SSH_COMMAND="ssh -i /opt/data/home/.ssh/id_ed25519_github_ka -o IdentitiesOnly=yes -o StrictHostKeyChecking=no" git push origin Kernel_Action
  ```
- Debug: `ssh -i <ka-key> -o IdentitiesOnly=yes -T git@ssh.github.com` prints `Hi DevHamid/Kernel_Action!` when the right key is loaded.
- A `Load key "...": bad permissions` warning during push does NOT mean the push failed — ssh falls back to another agent-held key and the push can succeed anyway. Trust the trailing `<old>..<new> <branch> -> <branch>` ref line (or `Hi <repo>!`), not the warning.
- If GitHub calls suddenly fail with `http=000`, `Connection reset by 64:ff9b::...`, or `kex_exchange_identification: read: Connection reset by peer`, the host's IPv6/NAT64 route is broken — force IPv4 (`curl -4`, `ssh -4`, or `AddressFamily inet` in `~/.ssh/config`) and retry before touching keys or remotes. If `-4` still resets on `api.github.com` (DNS returns an unreachable/AAAA-preferred address), pin a known-good IPv4 with `curl --resolve api.github.com:443:140.82.113.6 ...` — that bypasses DNS entirely and returns 200 where the bare host resets.
- Push with an explicit refspec naming the build branch (`HEAD:Kernel_Action`). A bare `git push origin HEAD` exits 0 without telling you which branch landed; confirm the trailing `<old>..<new> HEAD -> <branch>` line before assuming the workflow fired.
- The user sometimes commits to Kernel_Action directly (GitHub web UI). Before pushing your bump, `git fetch origin Kernel_Action && git rebase origin/Kernel_Action` — a stale local push is rejected as non-fast-forward, and you must rebase (not merge) to keep the branch linear. A `git pull` fails with the divergent-branches hint; the fetch+rebase is the recorded path.

## Boot image assembly: the mkbootimg image name must match the built artifact
- `config.env` carries two names: `KERNEL_IMAGE_NAME` (the file the compile step produces) and `KERNEL_IMAGE_NAME_MKBOOTIMG` (the file packed into `boot.img`). They must be the SAME string, and it must be the artifact that actually exists in `out/`.
- On an ARM64 QC tree with appended DTBs the artifact is `Image.gz-dtb`, and its layout is `gzip(Image)` followed by RAW DTB bytes — NOT `gzip(Image + DTB)`. Compressing the concatenation, or emitting a zlib container, yields a payload the kernel cannot decompress. Check the kernel slice's first two bytes: `1f 8b` = gzip (correct), `78` = zlib (wrong, bootloop).
- Do NOT assume `KERNEL_IMAGE_NAME_MKBOOTIMG=Image` is the bug. On a device with a `dtbo` partition (wayne/sdm660), a boot.img packing raw `Image` and ZERO appended DTBs boots fine — ABL takes the DTB from `dtbo`. Appending a DTB to boot.img makes the appended copy take PRECEDENCE, so what changes behaviour is the DTB CONTENT, not the naming. Establish which shape the known-good build shipped before touching config.env.
- Verify before blaming the kernel: `gzip -dc boot.img-payload | wc -c` on the extracted kernel region should equal the size of `out/arch/arm64/boot/Image` (or of `Image.gz-dtb` gunzipped). If the boot.img kernel payload is a plausible size but the DTBs are missing, the naming is the bug, not the compile.
- Fastest discriminator on a shipped `boot.img` (no unpack tools needed): read the header with `struct.unpack('<10I', data[8:48])[0]` for `kernel_size`, slice at page 4096, then check two bytes and the FDT count. Gzip payload → `1f 8b` at 0 and `\xd0\x0d\xfe\xed` appearing inside the slice. Raw ARM64 Image → `ARMd` (`41 52 4d 64`) at offset 56, `00 80` header stub at 0, and ZERO FDT magics — a boot.img that packs raw `Image` on an appended-DTB tree has no DTBs at all. Compare the suspect image against a known-good one field by field rather than reasoning from the kernel version string.
- Check the workflow reads the variable you edited: `grep -rn KERNEL_IMAGE_NAME_MKBOOTIMG .github/` — some steps hardcode `Image.gz-dtb` while others take the env var, so a config change can be a no-op on one path.

## Artifact provenance: audit the build that produced the image, not any build log lying around
- A tree accumulates several build dirs and logs; `build-<id>.log` + `config-<id>.txt` in one directory can belong to a DIFFERENT (often failed) build than the `config.txt`/`Image.gz-dtb`/`boot.img` in another. Cross-check timestamps and, decisively, prove the pairing: gunzip the gz prefix of `Image.gz-dtb` and assert it equals the kernel slice of `boot.img` (header `kernel_size`, offset 4096). Only then treat that config as authoritative for that image.
- Never conclude "config symbol X is missing" from a config file you have not tied to the image. A symbol present in the defconfig and absent from a stray config file is config drift between builds, not a defconfig bug — read the config that shipped with the artifact.
- Same rule for DTBs: parse the appended DTB embedded inside the built `Image.gz-dtb` at its real FDT offset, not a separately extracted `/tmp/*.dtb`. A stale or truncated standalone extraction reports zero reserved-memory children and no `ramoops` and sends you chasing a nonexistent DT bug. Enumerate every FDT magic in the file and pick the one with a sane `totalsize` before parsing.
- The in-tree DTS is only a starting point — the authoritative record is the appended FDT embedded in the specific boot image under test. A file-/node-level DTB diff can report "identical" while the property VALUES differ: comparing the booting reference against the new build showed the ramoops node present in both yet its `reg` moved (e.g. `0xa0000000` → `0x88f00000`). Always dump property-level values (ramoops `reg`, `console-size`, `pmsg-size`, `record-size`) from each decompressed kernel's FDT and diff those; node presence alone is not evidence of equality. Recipe: `references/ramoops-carveout-audit.md`.
- When a link-time cluster of `undefined symbol: __tracepoint_*` errors appears in one build log, check the successful build's image for the symbols (`k.count(b'__tracepoint_<event>')` on the kernel slice) before editing the tree — the fix may already have landed in a later commit.

## Isolating a bootloop: prove the A/B before bisecting anything
- **The embedded IKCFG config inside a boot image is frequently STALE — never use it as evidence.** Vendor trees ship an `IKCFG_ST`/`IKCFG_ED` span whose header still names an old release (e.g. reads `4.19.152` while the kernel is `4.19.325`). Diffing those spans across two images invents config differences that do not exist. The authoritative config is the `config.txt` committed to the `kbuilds` branch by the build that produced the image; read it with `git show FETCH_HEAD:config.txt`.
- Before bisecting, diff the two builds' actual kernel `Image` bytes. If they differ by <100 bytes the difference is a build timestamp + version-string hash, i.e. the SAME binary compiled twice — no config-level bisection between them is possible, and any config diff you computed is an artifact of the previous rule.
- A boot.img whose kernel slice is byte-identical to the bootlooping one but which boots proves the fault is in what surrounds the Image (appended DTB, ramdisk, cmdline), not in the kernel. Check header fields first: `page_size`, `kernel_addr`, `ramdisk_addr`, `tags_addr`, `cmdline`, ramdisk SHA-1.
- To separate "bad kernel" from "bad DTB" without device logs, repack candidate boot images from the same base and flash them in order: (1) new kernel + no appended DTB, (2) new kernel + the known-good stock DTB, (3) new kernel + our own DTB (control, must reproduce the loop). Build all three from one code path so the control is honest, and assert the header, ramdisk and cmdline are byte-identical to the reference before shipping. Recipe + script: `references/boot-image-forensics.md`, `scripts/bootimg_inspect.py`.
- Report these sessions in English only, terse and conclusion-first, including one-line transitions and retractions. Transitional sentences are where language slips happen; a Chinese connector inside an otherwise English verdict still reads as a language switch.

## Kernel-tree pitfalls
- The tree was re-imported as ONE squashed commit (`31333fe20`). Old historical SHAs (e.g. `5e34c146f97a`) no longer exist. Before planning a `git revert <sha>`, verify with `git cat-file -t <sha>` — if it fails, the fix must be hand-edited (e.g. disable a scheduler in `block/Kconfig.iosched` + defconfig).
- The `patch` tool refuses writes on `/srv/ssd/...` paths (both `ksrc/` and `kaction/`). Do config/file edits (config.env, defconfig) with a `python3` heredoc (assert the anchor is unique, replace, re-grep to verify).
- When demoting a default blk-mq I/O scheduler (e.g. clear `CONFIG_MQ_IOSCHED_DEFAULT_ADIOS`), the fallback must actually be compiled in. `block/elevator.c`'s `elevator_init_mq()` is an if/elif chain (`BFQ_DEFAULT` → `KYBER_DEFAULT` → `DEFAULT_ADIOS`) ending in `#else` that requests `"mq-deadline"`; if `CONFIG_MQ_IOSCHED_DEADLINE` is also unset, `elevator_get()` returns NULL and the queue silently gets the `none` scheduler. When demoting, also enable the fallback scheduler (flip `# CONFIG_MQ_IOSCHED_DEADLINE is not set` → `CONFIG_MQ_IOSCHED_DEADLINE=y`) and confirm it in the resolved `out/.config`.
- A `error: use of undeclared identifier '<SYMBOL>'` that fires only in one `.c` file usually means a backport dropped the symbol's declaration — grep the WHOLE tree (`git grep -n <SYMBOL> <branch>`) before blaming the toolchain or declaring the base broken. On the MGLRU `mglru-v5` branch `shrinker_rwsem` is referenced 7× in `mm/vmscan.c` but declared nowhere (upstream declares it in `include/linux/shrinker.h`); the fix is to re-add the `extern struct rw_semaphore shrinker_rwsem;` declaration. A make failure caused by a missing declaration survives any clean rebase — it will not vanish on a fresh base.

## Toolchain (Clang) selection for a 4.19 QC tree
- This 4.19 tree has NO `scripts/min-tool-version.sh` gate (that ships in newer kernels) — but its Makefile already gates on clang/lld ≥ 13 (POLLY flags at `CONFIG_CLANG_VERSION > 130000`, LTO `-plugin-opt` frame-warn when `CONFIG_LLD_VERSION < 130000`). Version 13–16 all satisfy it. Verify with `grep -n CLANG_VERSION \| LLD_VERSION \| POLLY_FLAGS Makefile`.
- Clang 17+ breaks old QC/4.19 trees (new default-flag errors, LTO `-plugin-opt` changes). **Clang 16 is the last universally-safe and the community norm** (ZyCromerZ, LKGT, sdm660 custom kernels). For 4.19 use `Clang-16.0.6` ZyCromerZ release.
- `config.env` defaults build with AOSP master clang (`CLANG_BRANCH=master`, `CLANG_VERSION=r547379` ≈ clang 20) — newer than a 4.19 tree wants. If random `-Werror`/LTO oddities appear, switch to ZyCromerZ Clang-16 first.
- **ZyCromerZ/Clang branches are NOT toolchain clones.** A branch (e.g. `16.0.6-20260807`) holds only txt metafiles (`Clang-16-link.txt`, `Clang-16-commit.txt`, `Clang-16-lastbuild.txt`) + README — no `bin/`. Do NOT set `CUSTOM_CLANG_SOURCE` to the repo URL; the workflow's `export PATH=.../clang-aosp/bin` would find nothing. Use the release **tarball** (the workflow's `*.tar.gz` branch wgets it straight into `clang-aosp/`, and the tar has `bin/` at root — verified working):
  ```
  USE_CUSTOM_CLANG=true
  CUSTOM_CLANG_SOURCE=https://github.com/ZyCromerZ/Clang/releases/download/16.0.6-20260807-release/Clang-16.0.6-20260807.tar.gz
  CUSTOM_CLANG_BRANCH=16.0.6-20260807
  ```
- ZyCromerZ tag-naming gotcha: release tag is `<ver>-<YYYYMMDD>-release` (`16.0.6-20260807-release`), branch is `<ver>-<YYYYMMDD>` (no `Clang-` prefix, no `-release`). The canonical current tarball URL for each major version always lives in the branch's `Clang-<major>-link.txt`. Verify the chosen tag's tarball exists (`curl -sI <download-url>` → 200) before committing config.env — a wrong/typo'd tag 404s inside the workflow step.
- ZyCromerZ tarballs bundle Binutils master + lld 16, so `EXTRA_CMDS:LD=ld.lld` keeps working. Read the current builds' versions off the GitHub releases page (release tags are `Clang-<ver>-<YYYYMMDD>`), not the README (it lists SDClang forks, not the releases).

## Hang vs panic: why pstore is empty
- **Magisk magic-mount shadows the pstore nodes — an empty `console-ramoops` is the FIRST thing to rule out before any hang/panic config theory.** A boot image built with Magisk injected into the ramdisk hides `/sys/fs/pstore/` behind its overlay, so `ls /sys/fs/pstore/` comes back empty even when the kernel captured a dump cleanly. Detect it by parsing the ramdisk cpio entries (see `references/boot-image-forensics.md`): presence of `.backup/` (with `init.xz`, `.magisk`, `.rmlist`) and `overlay.d/sbin/magisk32.xz` / `magisk64.xz` / `stub.xz`, plus a small `init` stub (~687 KB vs ~3 MB original), means Magisk is present and the dump zone is hidden. The fix is a clean boot image with Magisk removed entirely, re-uploaded, and `SOURCE_BOOT_IMAGE` in `config.env` pointed at the new image — not a kernel-side pstore patch.
- `kmsg_dump()` fires only on panic/oops. A silent hang (deadlock) logs nothing — empty `last_kmsg` / `console-ramoops` is expected, not a config bug.
- To convert future hangs into captured logs, ensure the defconfig has `CONFIG_DEBUG_KERNEL=y`, `CONFIG_SOFTLOCKUP_DETECTOR=y`, `CONFIG_DETECT_HUNG_TASK=y`, `CONFIG_BOOTPARAM_HUNG_TASK_PANIC=y`, and a positive `CONFIG_PANIC_TIMEOUT` (default `-1` = never reboot, so the captured panic is lost).
- Verify pstore is actually enabled in the defconfig (`CONFIG_PSTORE_RAM/CONSOLE/PMSG/LAST_KMSG=y`) and that the DTS carries a `ramoops` reserved-memory node before suspecting missing config.
- The `ramoops` node's `reg` must not overlap any other reserved-memory node NOR the QCOM `qcom,iommu-dma-addr-pool` region (an overlap makes the reservation silently fail — no probe, empty pstore). Pick a gap right after an existing carveout's end (e.g. `0x88F00000` sits exactly at `removed_regions1`'s end on sdm660) and confirm by listing the sibling reserved ranges.
- Diagnostic order when `console-ramoops` records nothing: (1) `dmesg | grep -iE "ramoops|pstore"` — want `pstore: Registered ramoops as persistent store backend` + `ramoops: using ...@0x<addr>`; (2) `cat /proc/iomem | grep -i ramoops` to confirm the reservation is live. If both are missing, the DT node isn't binding/reserving; if it probes but records are empty, apply the hang-vs-panic distinction above (panic goes to `dmesg-ramoops`, console only fills from normal printk console flow).
- Capture must be read on the reboot immediately following a crash: pstore only survives a `warm` reboot. A manual power cycle is a cold boot — the bootloader scrubs DRAM, so even a working ramoops shows empty `console-ramoops` after you power-cycle by hand. Trigger with `echo c > /proc/sysrq-trigger`, then read `/sys/fs/pstore/` on the auto-reboot (no manual power off in between).
- These debug options are a `depends on` chain: `SOFTLOCKUP_DETECTOR`, `DETECT_HUNG_TASK` → `DEBUG_KERNEL`, and `BOOTPARAM_HUNG_TASK_PANIC` → `DETECT_HUNG_TASK`. Enabling a child while dropping `DEBUG_KERNEL` silently no-ops it. Confirm what actually got enabled in `out/.config`, not in the defconfig.
- **`DEBUG_KERNEL=y` has a link-breaking side effect on QC vendor trees**: it flips the `FTRACE` default on, which selects `TRACEPOINTS=y`, turning every tracepoint reference into a real extern. Qualcomm TUs (e.g. `drivers/media/platform/msm/vidc_3x/*`) define their tracepoints in exactly one file whose Makefile line gates it on `CONFIG_DEBUG_FS` (e.g. `obj-$(CONFIG_DEBUG_FS) += msm_vidc_debug.o`). If `DEBUG_FS` is unset, the build fails at LINK with `ld.lld: error: undefined symbol: __tracepoint_...` (a whole cluster, one per event), not at compile. When enabling `DEBUG_KERNEL` on such a tree, also enable `CONFIG_DEBUG_FS=y`; otherwise debug the link error by grepping the resolved `out/.config` for `DEBUG_FS` and the `Makefile` gates on the tracepoint-defining TU.
